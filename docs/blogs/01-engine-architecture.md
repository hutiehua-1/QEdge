# 从比赛脚本到分层推理引擎：QEdge 的多模态执行链路

> 摘要：围绕 Qwen3.5-2B 的多模态单选题推理，我们把消息处理、调度、缓存与模型执行拆成独立职责。本文介绍 QEdge 的代码组织和性能分析方法，帮助读者定位一次请求在推理系统中的执行位置。
>
> 状态：基于 v1.0 的投稿初稿；目标为 PPU/SAIL 环境，本次整理未进行设备复测。

## 为什么先整理执行链路

图片和问题进入模型后，并不是一次矩阵乘法就得到答案。Processor 需要组织图片与文本，Prefill 计算输入历史，Decode 逐步生成 token，输出还需要经过文本解码与计时。若把这些阶段全部放在一个生成函数里，即使总时间下降，也很难知道收益来自输入变化、缓存复用还是计算路径。

QEdge 的做法是保留比赛要求的外部接口，在内部划分控制层、数据层和计算层。这让优化有具体的落点，也使对照实验可以围绕开关和状态边界展开。

## 接口保持，内部执行改变

公开入口仍是 `VLMModel.generate_with_metrics`，输入包含图片、prompt、选项和生成参数，返回文本、token 数、TTFT、总耗时及元数据。它把模型实现与评测入口分开，但“接口兼容”不意味着内部仍调用原来的生成实现。

代码保留 `--backend transformers` 这一比赛兼容名称，实际加载 `Qwen35Engine`。读者复现时需要特别留意：`auto` 加载失败可降级为 dummy，所以真实评测应明确选择 `transformers`，让环境问题直接暴露。

## 三层各自负责什么

控制层包含 Engine 和 Scheduler。Engine 负责模型与处理器的初始化、接收请求和驱动生成；Scheduler 则根据 Token 预算、可用缓存页和请求进度，决定本步执行哪些 Prefill 或 Decode。

数据层管理 Sequence、物理页、前缀索引和混合状态。它处理的不只是“还能放多少 token”，还包括“哪些历史可以恢复”“恢复点有没有匹配的线性层状态”“回收页时索引是否失效”。这类约束直接影响结果正确性。

计算层由 Executor、ModelRunner、模型封装和算子组成。它承接调度结果，准备输入与缓冲区，执行模型，并处理图捕获与回放。Norm、Attention、Gated DeltaNet 等实现位于更下层，便于按计算形态选路。

```text
图片 + 问题
  → wrapper / Processor
  → Engine / Scheduler
  ↔ KVManager / Sequence / 前缀索引
  → Executor / ModelRunner
  → 模型与算子
  → token / 文本 / 计时结果
```

## 输入处理也是实验变量

项目会识别公开单选题的固定说明，在允许复用时把它放入图片之前的 system 消息，把图片与动态问题留在 user 消息。这样稳定文本可以获得不依赖当前图片的前缀。

这一变化会改变消息角色与顺序。因此，它不能被描述成“输入完全相同，只优化了底层 kernel”。严谨的对照需要分别观察输入组织、缓存、算子路径的影响，并同时检查答案质量。

## 如何理解现有数字

随源码保存的一份英文开发集结果包含 2000 个样本，记录 1613 个正确答案，即 80.65%；平均 TTFT 为 60.449 ms，平均样本解码吞吐为 680.489 tokens/s。逐条记录重算与汇总一致。

这些数字是历史结果文件中的记录，缺少完整硬件、依赖版本和模型 revision，本次没有独立复现。吞吐是样本级数值的算术平均，不是整个服务在总时间内的输出率。它们可以作为补做实验的线索，不能直接与另一份不同规模的 baseline 算出加速比。

## 读者可以先验证什么

无需设备，也可以检查配置合法性、页引用计数、淘汰和媒体哈希边界。项目的主机测试直接加载这些纯逻辑模块，不需要伪造 GPU 张量。

真正判断优化是否有效，还需要目标设备上的参考输出对照、冷启动与稳态测量、相同数据和生成参数的消融实验。分层的价值在于帮助我们组织这些验证；架构存在本身不构成性能证明。
